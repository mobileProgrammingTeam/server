# 작업자 생성 버튼 및 관리자 화면 실데이터 표시 개선 계획

작성일: 2026-11-02 (Asia/Seoul)

## 1. 해결할 문제와 적용 기준

로그인 후 작업자 생성 기능을 바로 찾고 실행할 수 있게 하고, 생성·입력·측정하지 않은 예시 데이터가 관리자 화면에 표시되는 경로를 제거한다.

이전 계획은 “미구현 API의 고정 DTO 반환 유지”를 “해당 DTO의 화면 표시도 허용”하는 의미로 해석했다. 그 결과 고정 데이터가 MVC와 JS를 통해 계속 표시되었다. 이번에는 다음 기준을 적용한다.

- 미구현 도메인 API의 정식 경로·DTO·고정 반환·TODO는 서버 코드에 유지한다.
- 관리자 화면은 실제 저장된 데이터와 구현된 조회 결과를 사용한다. 미구현 API의 고정 응답은 화면의 최초 렌더링·자동 조회·실패 대체값으로 사용하지 않는다.
- 아직 수집하거나 저장할 수 없는 값은 `-`, `데이터 없음`, `연동 준비 중`으로 표시한다.
- 기존 실제 생성·조회·이벤트 처리·인증 기능을 사용한다. 미구현 도메인의 새 비즈니스 로직은 추가하지 않는다.

이 문서는 앞선 두 이전·정리 계획의 데이터 표시 기준보다 우선한다. 이번 작업은 계획서 작성이며 애플리케이션 코드 변경과 테스트 실행은 구현 단계에서 진행한다.

## 2. 코드에서 확인한 사실과 추가 확인 사항

| 항목 | 확인한 사실 | 문제 또는 확인할 점 |
| --- | --- | --- |
| `workers.html` | `/admin/workers`의 `worker-form` 안에 ‘작업자 추가’ 제출 버튼이 있음 | 소스 전체에서 버튼이 없는 상태는 아님. 실제 제공되는 화면과 소스의 일치 확인 필요 |
| `fragments.html` 공통 상단바 | 설정·관리자 관리·로그아웃만 있음 | 로그인 직후 작업자 생성 기능을 바로 찾기 어려움 |
| `dashboard.html` | 작업자 목록 이동 링크는 있으나 생성 버튼 없음 | 첫 로그인과 빈 데이터 상태의 생성 진입점 부족 |
| 작업자 생성 JS | 생성 성공 후 임시 비밀번호 표시와 폼 초기화만 수행 | 목록을 갱신하지 않아 생성된 작업자가 나타나지 않은 것으로 보일 수 있음 |
| 작업자 생성 폼 | 나이가 `25`로 미리 입력되어 있음 | 사용자가 입력하지 않은 업무 값이 전송될 수 있음 |
| `AdminWebController` | 여러 화면의 Model에 `AdminUiFixtures`를 직접 주입 | 처음 로그인해도 가상 작업자·이벤트·구역·기상·관리자 등이 표시됨 |
| `loadWorkerStatus` | 실제 작업자 목록·상세에서 `/api/admin/workers/{id}/status` 자동 호출 | 생성한 실제 작업자에게 고정 위험·구역·생체·NFC 상태를 붙임 |
| 고정 작업자 상태 API | 요청 ID와 첫 번째 샘플의 나머지 필드를 조합해 반환 | 작업자 ID가 실제 ID여도 상태가 실제 측정값이라는 의미는 아님 |
| `dashboard.html` 및 공통 head | 같은 `admin.js`를 각각 포함 | 대시보드에서 동일 코드가 중복 실행될 수 있음 |

CSS에서 생성 버튼을 명시적으로 숨기는 규칙은 현재 소스 검토로 확인되지 않았다. 실제 실행 중인 서버·브라우저는 이번 계획 작성에서 재현하지 않았으므로 버튼 미노출의 최종 원인은 구현 첫 단계에서 확인한다.

### 2.1 구현 시작 시 재현 절차

1. 현재 접속 URL·포트·로그인 후 이동 경로와 실행 프로세스의 JAR 또는 작업 디렉터리를 확인한다.
2. 로그인 후 실제 HTML에 작업자 관리 링크·생성 폼·제출 버튼이 있는지 확인한다.
3. 실제 응답과 현재 템플릿이 다르면 빌드·실행 대상·정적 파일 갱신을 먼저 바로잡는다.
4. HTML은 맞지만 버튼이 안 보이면 실제 화면 크기, computed style, 요소 크기, 스크롤·겹침 여부를 확인한다.
5. 클릭이 동작하지 않으면 JS 오류와 이벤트 등록, 네트워크 요청, 401·403 응답을 확인한다.

버튼이 소스에 있다는 사실이나 HTTP 200만으로 사용자 문제를 해결했다고 판단하지 않는다.

## 3. 로그인 후 작업자 생성 흐름

### 3.1 생성 버튼의 위치와 동작

- 로그인된 관리자 공통 상단바에 **‘+ 작업자 생성’** 버튼 형태의 링크를 추가한다.
- 링크는 `/admin/workers#worker-create`로 이동한다. 생성 섹션에 해당 ID를 부여한다.
- 작업자 관리 화면의 생성 폼은 빈 목록 여부와 관계없이 표시한다. 제출 버튼 문구는 **‘작업자 생성’**으로 통일하고 `type="submit"`을 명시한다.
- 빈 작업자 목록에는 ‘등록된 작업자가 없습니다’와 동일 생성 폼으로 이동하는 진입점을 표시한다.
- 버튼에 범위가 명확한 주 버튼 스타일을 적용해 일반 조회·설정 버튼과 구별한다. 모바일에서도 접힘·가로 스크롤 뒤에 감춰지지 않게 배치한다.
- 공개 로그인 화면에는 생성 버튼을 노출하지 않는다. 기존 `/admin/register`는 관리자 로그인 후 작업자 관리로 이동하는 호환 경로로 유지한다.

별도의 가입 화면이나 생성 API는 추가하지 않는다.

### 3.2 입력과 실제 생성

기존 `POST /api/admin/workers`에 `workerName`, `sex`, `age`를 전송한다. 관리자 세션·CSRF 검사를 유지한다.

- 이름과 나이는 빈 값으로 시작한다. 나이 `25` 같은 예시 업무 값을 `value`로 넣지 않는다.
- 성별은 ‘선택하세요’를 초기 항목으로 제공하고, 사용자가 남성·여성·미지정을 선택하도록 한다.
- API가 요구하는 필수값·범위를 그대로 검사한다. 빈 나이를 JS에서 `Number('')`로 변환해 0으로 전송하지 않는다.
- 전송 중 제출 버튼을 잠그고, 실패하면 입력값과 오류를 표시한다.
- 공통 JS는 한 번만 로드해 같은 클릭에서 중복 요청을 만들지 않는다.

### 3.3 생성 결과 확인

- 201 응답의 작업자 ID와 임시 비밀번호를 결과 영역에 표시한다.
- 생성된 ID의 실제 상세 조회 결과와 상세 이동 링크를 제공해 생성 성공을 확인할 수 있게 한다.
- 목록·페이지 영역만 Thymeleaf fragment로 다시 조회한다. 임시 비밀번호 결과 영역은 교체하지 않는다.
- 목록의 기존 ID 오름차순과 페이지 계약을 유지한다. 새 작업자가 현재 페이지에 포함되지 않으면 생성 결과의 상세 링크로 확인하게 하고, 임의 행을 현재 페이지에 끼워 넣지 않는다.
- 목록 갱신 실패는 생성 실패와 구분한다. 이미 생성된 작업자를 확인하려고 POST를 자동 재시도하지 않는다.
- 비밀번호를 URL, 로그, localStorage, sessionStorage, 서버 세션에 보관하지 않는다. 화면 이동 후 다시 표시하려고 저장하지 않는다.

필요한 fragment는 기존 `/admin/workers` 조회에 허용된 목록 fragment 선택만 추가하여 제공한다. 사용자 입력으로 임의 템플릿 이름을 지정하지 않는다.

## 4. 입력하지 않은 데이터의 화면 유입 차단

### 4.1 서버 렌더링

- `AdminWebController`에서 `AdminUiFixtures` import와 화면 Model 주입을 제거한다.
- 대시보드·작업자·이벤트는 이미 구현된 `SafetyService` 조회를 사용한다.
- 미구현 화면은 빈 목록, 누락된 값, 조회 가능 여부를 명확히 표현한 Model을 전달한다. 빈 상태를 만들기 위해 고정 API의 DTO 계약을 변경하지 않는다.
- HTML의 숨김 속성·`data-*`·인라인 JSON에도 샘플 행을 남기지 않는다. CSS로만 숨기는 방식은 사용하지 않는다.
- 수치가 실제 0인지, 아직 알 수 없는지 구분한다. 실제 빈 목록의 개수는 0이고 미수집 위험·통신 통계는 `-`다.

### 4.2 브라우저의 자동 조회

- 실제 작업자 목록과 상세에서 고정 status API를 자동 호출하는 `loadWorkerStatus` 연결을 제거한다.
- 해당 API의 상태를 실제 작업자 ID와 조합해 생체신호·위험도·위치·마지막 통신에 표시하지 않는다.
- 고정 이벤트용 모달과 DOM 데이터, 고정 설정·기상·관리자 목록을 표시하는 호출부를 제거한다.
- 실패 시 샘플로 대체하거나, ‘미배정’·‘정상’·‘오프라인’을 근거 없이 확정하지 않는다.
- ‘확인 중’은 실제 조회가 진행되는 동안만 사용한다. 조회 자체가 미구현이면 ‘정보 없음’ 또는 `-`로 표시한다.

### 4.3 미구현 변경 기능

고정 반환 API만 있는 관리자 추가·역할·활성 변경, 설정 저장, 날씨 메시지, NFC 요청, SOS, 신규 확인/해결 등의 버튼은 실제 업무 완료로 오해되지 않게 처리한다.

- 화면 구조와 입력 영역은 유지하되 실행 버튼을 비활성화하고 짧은 ‘준비 중’ 안내를 제공한다.
- 화면에서 고정 변경 응답을 받아 저장·발송 완료로 표시하지 않는다.
- 실제 구현된 작업자 생성·비밀번호 초기화·기존 이벤트 `process`는 계속 동작한다.
- API의 정식 매핑과 DTO·고정 return·TODO는 유지한다. 비즈니스 로직은 추가하지 않는다.

## 5. 화면별 변경 내용

| 화면 | 실제 표시할 데이터 | 아직 없는 데이터 처리 |
| --- | --- | --- |
| 대시보드 | 실제 작업자 수·전체/미처리 이벤트 수·최근 실제 이벤트·실제 작업자 기본정보 | 위험도·오프라인·생체·구역별 통계는 `-` 또는 빈 상태. 고정 우선 경고 배너 제거 |
| 작업자 목록 | DB의 ID·이름·성별·나이·계정 상태 | 안전·구역·생체·통신 값은 `-`; 고정 status API 자동 호출 중단 |
| 작업자 상세 | 실제 작업자 기본정보·해당 작업자의 실제 이벤트 | 측정·NFC·기기·위치 정보는 미수집 상태. 관련 미구현 명령 비활성화 |
| 이벤트 이력·상세 | 기존 실제 이벤트와 처리 메모·처리자·처리 시각 | 존재하지 않는 위험도·구역·확인 단계·통신값을 보충하지 않음 |
| 긴급 알림·대응 | 기존 실제 미처리 이벤트 조회와 실제 `process` 동작 | 실제 미처리를 임의로 CRITICAL·NEW·ACKNOWLEDGED 등으로 변환하지 않음. 신규 단계 기능은 준비 중 |
| 구역·구역 상세 | 현재 실제 조회 기능이 없으므로 등록/조회 준비 상태 | A/B 구역·소속 작업자·거리·체류·경고·대응 샘플 제거. 임의 ID 접근을 샘플 A 구역으로 대체하지 않음 |
| 기기·통신 | 실제 작업자 목록을 표시할 경우 신원만 사용 | 연결·기기·측정·오프라인 통계는 데이터 없음. 정상/오프라인을 가정하지 않음 |
| 날씨 | 연동되지 않은 상태 표시 | 고정 온도·습도·시각·공지 제거. 입력한 공지를 저장한 것처럼 추가하지 않음 |
| 처리 기록·보고서 | 기존 실제 완료 이벤트에서 처리 시각·관리자 ID·메모 조회 | 미구현 감사 로그는 빈 상태. 기존 process를 별도 acknowledge/resolve 감사 기록으로 꾸미지 않음 |
| 설정 | 실제 저장된 해당 설정이 없다는 상태 | 고정 5분·15분·HIGH를 저장된 설정으로 표시하지 않음. 저장 비활성화 |
| 관리자 관리 | 필요하면 현재 세션의 실제 로그인 ID·권한만 표시 | 샘플 관리자·이메일·역할 목록 제거. 전체 관리자 조회·등록/변경은 준비 중 |

대시보드 최근 이벤트는 `service.dashboard().recentEvents`를 사용한다. 기존 `EventInfo`의 필드에 맞춰 템플릿을 바꾸며 UiEvent의 위험도·구역·상태를 덧붙이지 않는다.

보고서의 전체 개수는 실제 조회의 `totalElements` 또는 기존 실제 대시보드 집계를 사용한다. 한 페이지의 행 개수를 전체 이벤트 수로 표시하지 않는다. CSV는 실제 표시된 기록만 내보내며 빈 결과에서는 비활성화한다.

## 6. 기존 DB 데이터 처리

실제 DB에 저장된 작업자·이벤트는 로그인한 관리자 본인이 이번 세션에 입력하지 않았어도 표시할 수 있다. 현재는 관리자별 데이터 소유 구분이 없는 공동 관리 구조다. 사용자별 격리를 임의로 추가하지 않는다.

화면 정리를 위해 DB 파일·테이블·기존 계정을 초기화하거나 자동 삭제하지 않는다. DB에 남아 있는 테스트 입력이 의심되면 샘플 표시 경로와 저장 레코드를 구별해 확인하고, 삭제가 필요한 경우에는 별도 대상과 기준을 정한다. 테스트 검증에는 운영·개발 DB와 분리한 임시 DB를 사용한다.

| `templates/admin/fragments.html` | 로그인 후 공통 생성 버튼과 목적지 추가 |
| `templates/admin/workers.html` | 생성 영역 ID·명확한 제출 버튼·빈 입력·생성 결과·목록 fragment |
| `static/css/admin.css` | 생성 버튼의 색·대비·모바일 배치에 필요한 범위 수정 |
| `static/js/admin.js` | 생성 후 실제 상세·목록 확인, 고정 응답 자동 조회·가상 표시·미구현 명령 실행 제거 |
| `controller/web/AdminWebController.java` | 화면 fixture 의존 제거, 기존 실제 조회 연결, 미구현 화면의 빈 상태 Model, 목록 fragment |
| `templates/admin/dashboard.html` | 실제 대시보드 데이터 사용, 생성 버튼 진입 확인, JS 중복 로드 제거 |
| 나머지 관리자 템플릿 | 실제 데이터/빈 상태 렌더링, 샘플 `data-*` 제거, 미구현 버튼 비활성화 |
| 통합·브라우저 검증 | 생성 버튼 클릭부터 실제 저장 확인까지 검증, 모든 메뉴의 샘플 미표시 검증 |
| `README.md`, 기존 계획서 | API 고정 응답 보존과 화면 실데이터 기준 명시 |

`AdminDomainApiController`와 고정 DTO 정의는 보존한다. 해당 API를 삭제하거나 응답을 빈 DTO로 바꾸어 화면 문제를 해결하지 않는다. 실제 데이터 연결을 위해 새 도메인 Entity·테이블·외부 전송 로직은 추가하지 않는다.

## 8. 실행 순서와 완료 검증

1. 실행 중인 화면을 재현하고 소스·빌드·제공 HTML 일치를 확인한다. → 버튼 미노출의 실제 지점과 화면별 데이터 출처를 기록한다.
2. 공통 생성 버튼과 기존 폼 연결을 수정한다. → 로그인 직후와 빈 목록에서 생성 폼까지 한 번의 버튼 클릭으로 이동한다.
3. 생성 결과와 실제 상세·목록 조회를 연결한다. → 한 번의 제출로 계정 하나가 생성되고 결과·목록이 실제 DB와 일치한다.
4. 모든 MVC·JS의 고정 응답 표시 경로를 제거한다. → 초기 렌더링 후 JS가 실행되어도 샘플 데이터가 다시 나타나지 않는다.
5. 미구현 화면·버튼을 빈 상태와 준비 상태로 정리한다. → 임의 값·저장/발송 성공 표시가 없다.
6. 깨끗한 빌드와 실제 브라우저 흐름을 검증한다. → 아래 완료 조건을 충족한 결과를 기록한다.

### 8.1 자동 검증

- 임시 DB에 관리자 계정만 있는 상태에서 작업자 0명·이벤트 0건을 표시하고 샘플 행이 없는지 확인한다.
- 초기 HTML뿐 아니라 JS 실행 이후 DOM에도 고정 DTO의 이름·ID·기상·구역·관리자 목록이 유입되지 않는지 확인한다.
- 로그인한 관리자는 생성 API를 호출할 수 있고, 익명·작업자 Bearer·CSRF 누락 요청은 생성하지 못하는지 확인한다.
- 생성 버튼으로 입력한 이름·성별·나이가 DB·응답·상세·목록과 일치하고 중복 제출되지 않는지 확인한다.
- 실제 작업자만 생성된 상태에서 위험·심박·구역·통신값이 자동 채워지지 않는지 확인한다.
- 실제 이벤트를 등록하면 그 작업자의 실제 이벤트가 표시되고, 처리 시 기존 저장 결과가 반영되는지 확인한다.
- 화면 코드가 stub 조회·명령 API를 자동 호출하지 않는지 확인한다. 유지하는 API의 경로·DTO·무저장 계약은 별도 검증한다.
- 생성 결과의 비밀번호가 새로고침·URL·저장소·로그에 보존되지 않는지 확인한다.
- 목록 갱신 실패가 생성 POST 재시도를 유발하지 않는지 확인한다.
- `.\mvnw.cmd clean verify`로 수정한 소스를 전체 재컴파일하고 기존 회귀 검증을 수행한다.

샘플 문자열이 있다는 사실만 검사하지 않는다. 실제로 동일 이름의 작업자를 만들 수 있으므로, 생성한 레코드와 화면 행의 ID·값·개수를 비교하고 fixture 호출·네트워크 유입 경로도 검증한다.

### 8.2 실제 브라우저 검증

- 로그인 → 대시보드의 생성 버튼 → 입력 → 실제 생성 → ID·임시 비밀번호 확인 → 상세/목록 확인 흐름을 수행한다.
- 1440px·1024px·390px·320px에서 버튼의 실제 크기·표시·클릭·키보드 접근을 확인한다. HTML 문자열 존재만으로 통과시키지 않는다.
- 버튼 텍스트가 배경에 묻히거나 컨테이너 밖으로 밀리지 않는지 확인한다.
- 네트워크 탭에서 제출 한 번에 생성 POST가 한 번만 발생하고 status stub 호출이 없는지 확인한다.
- 신규 DB와 실제 데이터가 있는 DB에서 모든 메뉴를 순회하며 샘플이 재등장하지 않는지 확인한다.
- 오류·세션 만료·목록 갱신 실패·빈 상태를 확인하고, 개발 DB의 자동 삭제가 없는지 확인한다.

## 9. 완료 조건

- 관리자가 로그인한 모든 주요 화면에서 작업자 생성 버튼을 바로 찾고 사용할 수 있다.
- 실제 작업자 생성과 생성 결과 확인이 브라우저에서 동작한다.
- 생성하지 않은 가상 작업자·이벤트·관리자·구역과 측정하지 않은 상태값이 관리자 화면에 표시되지 않는다.
- 고정 DTO 반환 API는 정식 계약과 TODO를 유지하지만 관리자 화면의 데이터 공급 경로에서는 제외된다.
- 실제 저장 데이터의 조회·생성·처리 기능과 보안이 유지된다.
- 자동 검증 결과와 실제 브라우저 검증 결과를 구분해 완료 보고에 기록한다.
