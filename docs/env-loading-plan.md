# 로컬 .env 자동 로드 구현 계획

## 목적과 전제

프로젝트 루트를 작업 디렉터리로 사용하는 IntelliJ 실행에서 `.env`의 초기 관리자 정보를 자동으로 읽도록 한다. 현재 기본 프로필인 `local`에 적용한다. 운영의 환경변수 주입 방식과 기존 관리자 계정 보존 정책을 유지한다.

현재 `AdminBootstrap`은 Spring의 `@Value`로 `ADMIN_LOGIN_ID`, `ADMIN_INITIAL_PASSWORD`를 읽는다. 따라서 Spring 설정 소스에 파일을 추가하면 기존 초기화 코드를 사용할 수 있다.

## 구현 방식

새 `src/main/resources/application-local.properties`에 다음을 추가한다.

```properties
spring.config.import=optional:file:./.env[extension=.properties][encoding=utf-8]
```

- Spring Boot 4.1.2의 기본 설정 가져오기 기능을 사용한다. 별도의 dotenv 라이브러리나 POM 변경은 필요하지 않다.
- `.env`는 현재 작업 디렉터리에서 찾는다. IntelliJ의 Working directory를 `pom.xml`이 있는 프로젝트 루트로 설정한다.
- `.env`가 없어도 파일 로딩 오류는 발생하지 않는다. 최초 관리자도 없고 필요한 값도 없으면 기존 초기화 검증이 명확한 오류로 기동을 중단한다.
- 이 파일은 UTF-8 Java Properties 형식으로 해석한다. OS 프로세스의 환경변수를 수정하는 기능은 아니다.
- 운영체제·IntelliJ 환경변수와 명령행 설정은 파일보다 우선한다. 실제 구현 테스트에서도 이 우선순위를 검증한다.
- `prod` 프로필에서는 로컬 파일을 자동으로 가져오지 않는다. Docker Compose는 기존처럼 호스트 `.env`를 읽어 컨테이너 환경변수로 전달한다.

공식 근거: [Spring Boot 외부 설정 문서](https://docs.spring.io/spring-boot/reference/features/external-config.html). 파일 가져오기, 확장자·인코딩 속성 및 설정 소스 우선순위를 따른다.

## 변경할 파일

| 파일 | 변경 내용 |
| --- | --- |
| `src/main/resources/application-local.properties` | 로컬 전용 `.env` 가져오기 설정 추가 |
| `.env.example` | IntelliJ·로컬 실행에도 사용하는 예제로 설명 수정, 선택적 DB 경로 안내 |
| `README.md` | 복사·값 입력·작업 디렉터리·재시작·문법·우선순위 안내 추가 |
| `docs/implementation-instructions.final.md` | 기존 `.env` 수동 주입 설명을 로컬 자동 로드 정책과 일치시킴 |
| 기존 통합 테스트 | `test` 프로필을 명시해 개발자의 실제 `.env`로부터 격리 |
| 설정 로딩 테스트 | 임시 파일과 무작위 값을 이용해 실제 Config Data 로딩 검증 |

`.gitignore`와 `.dockerignore`는 이미 `.env`를 제외하고 있다. 이 제외가 유효한지 확인한다. 기존 사용자 수정이 있는 `pom.xml`은 이 작업에서 수정하지 않는다.

## 단계별 작업과 검증

1. **로컬 설정 연결**: `application-local.properties`를 추가한다. → 검증: 별도의 OS 관리자 환경변수 없이 임시 `.env` 값을 Spring Environment와 `AdminBootstrap`이 읽는다.
2. **예제·문법 정리**: `.env.example`을 갱신한다. 관리자 값은 빈 칸으로 두고 사용자가 정한 값을 입력하도록 안내한다. → 검증: 예제에는 실제 비밀번호나 고정 공용 계정이 없다.
3. **사용 문서 갱신**: IntelliJ에서 프로젝트 루트를 작업 디렉터리로 지정하고 `.env.example`을 `.env`로 복사하여 실행하는 절차를 작성한다. → 검증: 파일 수정 후 서버 재시작이 필요함을 명시한다.
4. **테스트 격리·설정 검증**: 기존 테스트는 `test` 프로필과 기존 임시 DB·무작위 계정을 유지한다. 별도의 설정 테스트에서만 임시 `.env`를 가져온다. → 검증: 개발 DB나 실제 `.env`를 읽거나 변경하지 않는다.
5. **전체 빌드·실행 확인**: `.\mvnw.cmd clean verify` 후 패키징된 서버를 임시 DB·임시 설정으로 실행한다. → 검증: 최초 관리자 생성·로그인·재시작 후 기존 비밀번호 유지 확인.

## 필수 확인 사례

| 조건 | 기대 결과 |
| --- | --- |
| `local` + `.env` 있음 | 파일의 관리자 ID·비밀번호, 포트·토큰 수명 설정 로드 |
| 같은 키의 파일 값과 환경변수 값이 다름 | 환경변수 값 우선 |
| `.env` 없음 + 환경변수 있음 | 기존 환경변수 방식으로 기동 |
| `.env` 없음 + 기존 관리자 있음 | 초기 자격증명 없이 기동 |
| 최초 실행에서 관리자 필수값 누락·빈 값 | 기존의 명확한 초기화 오류 유지 |
| 기존 관리자 존재 + `.env` 비밀번호 변경 | DB의 관리자 비밀번호를 덮어쓰지 않음 |
| `prod` 또는 `test` 프로필 | 로컬 프로필의 `.env` 가져오기 미적용 |
| UTF-8 값 및 비밀번호 길이 경계 | 파일값을 정확히 읽고 기존 12~64자·72바이트 정책 적용 |

설정 소스 우선순위는 실제 Spring 설정 로더로 검증한다. 파일 내용을 문자열로 읽는 것만으로 로딩 테스트를 대체하지 않는다.

## .env 사용 규칙

- `KEY=value` 형식을 사용하고, 값에 불필요한 앞뒤 공백이나 감싸는 따옴표를 넣지 않는다. `export KEY=value` 같은 셸 구문을 사용하지 않는다.
- 이 방식은 Java Properties 파싱이므로 일반 dotenv의 모든 문법을 지원한다고 설명하지 않는다. 백슬래시와 따옴표 등의 해석 차이를 안내하고 Windows 파일 경로는 `/` 사용을 권장한다.
- Docker Compose의 보간 문법은 별도이므로, 같은 `.env`를 양쪽에서 사용할 때 `$`, 백슬래시 등의 값 해석 차이를 문서화한다. 비밀번호를 조용히 변환하거나 trim하지 않는다.
- 실제 `.env`는 저장소에 커밋하거나 JAR·Docker 이미지에 포함하지 않는다. 테스트 및 실행 점검에서도 값을 로그에 출력하지 않는다.
- 프로필 선택은 IntelliJ·환경변수 등 외부 실행 설정에서 한다. `local`에서 가져오는 `.env`에 프로필 선택을 의존하지 않는다.

## 완료 기준

IntelliJ 실행 구성에 관리자 자격증명을 따로 입력하지 않아도 프로젝트 루트의 `.env`로 최초 관리자 생성과 로그인이 가능해야 한다. 설정 우선순위·파일 부재·기존 계정 보존 테스트 및 기존 서버 테스트가 통과해야 한다. 배포 프로필과 비밀값 제외 정책도 유지되어야 한다.

이 문서는 구현 계획이며, 아직 설정이나 애플리케이션 코드를 변경한 결과는 아니다.
